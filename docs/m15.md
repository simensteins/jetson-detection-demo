# M15 – optimizing the stakeholder's YOLO11-based detector

M15 is a YOLO11s with an extra stride-4 (P2) detection head for small objects: one class, 1-channel grayscale input, trained at 960×960 (architecture: `models/m15/yolo11s-p2-m15.yaml`). The trained weights are the stakeholder's and are not in this repo.

## Pipeline

| Step | Script | Notes |
|---|---|---|
| Training checkpoint → Ultralytics `.pt` | `scripts/build_m15_pt.py` | Rebuilds the architecture and loads the EMA weights strictly (any mismatch is an error). |
| `.pt` → ONNX → TensorRT | `scripts/export_m15.py --precision fp32-tf32 \| fp32-strict \| fp16` | ONNX: static 1×1×960×960 input, output (1, 5, 76500), no NMS inside. `fp16` builds FP16 layers **and** FP16 I/O. Engines must be built on the Jetson. |
| Inference | `scripts/infer_m15_trt.py --engine <file.engine>` | Stage flags: `--no-graph`, `--preprocess cpu\|gpu`, `--nms torchvision\|fixed`, `--nms-candidates k`. Dtypes are read from the engine. Config: `configs/m15-fast.yaml`. |

Stage commands (as in `scripts/profile_paper_set.sh`):

| Stage | Flags |
|---|---|
| Baseline | `--engine m15_fast_fp32-tf32.engine --no-graph --preprocess cpu` |
| + CUDA graph | `--engine m15_fast_fp32-tf32.engine --preprocess cpu` |
| + GPU preprocessing | `--engine m15_fast_fp32-tf32.engine` |
| + FP16 | `--engine m15_fast_fp16.engine` |
| + Custom NMS (eager) | `--engine m15_fast_fp16.engine --nms fixed` |

## Results (paper set, 25 W, 1920×1080)

| Stage | FPS | Frame time | GPU kernels |
|---|---|---|---|
| Baseline | 19.1 | 52.4 ms | 43.8 ms |
| + CUDA graph | 19.6 | 50.9 ms | 43.0 ms |
| + GPU preprocessing | 20.2 | 49.6 ms | 44.4 ms |
| + FP16 | **40.3** | 24.8 ms | 19.6 ms |
| + Custom NMS (eager, k = 1000) | 34.6 | 28.9 ms | 22.6 ms |

Figures and the detailed breakdown: [results-paper25w.md](results-paper25w.md).

## What we learned

**1. The model is the bottleneck.** In FP32 the GPU kernels are ~83 % of the frame. Removing overhead (CUDA graph, GPU preprocessing) can only work on the rest, so it gives 1.06× here against 1.47× for YOLOv8n (Amdahl's law). FP16 halves the model (44.4 → 19.6 ms) and doubles the FPS.

**2. Where FP16 helps.** In the TF32 engine, fused elementwise kernels (`generatedNativePointwise`, memory-bound on the large stride-4 feature maps) took 18.6 ms per frame; in FP16 they take 1.4 ms. After FP16, the largest remaining item is layout conversion kernels (`permutationKernelPLC3`, `nhwcTonchw`, ~3.3 ms) – a candidate for Nsight Compute.

**3. GPU preprocessing has to be written for the GPU.** The first version converted the frame to grayscale with a matrix product (`@ gray_w`), which ran as a cuBLAS `gemv` kernel taking ~4 ms per 1920×1080 frame, after converting the full frame to float. Fixed in `8fb2331`: resize first, then a weighted sum on the 960×540 result, letterbox border filled once. Output identical to within 2×10⁻⁷. GPU preprocessing 5.4–7 ms → 1.3 ms.

**4. A fixed-shape NMS does not pay off on its own.** `--nms fixed` is a fixed-shape Cluster-NMS (exact: matches `torchvision.ops.nms`. The "Fast NMS" approach of YOLO's Iteration 3 dropped 7–19 boxes that standard NMS keeps in synthetic crowded M15-shaped scenes, so it was not reused). It removes the GPU→CPU waits of the torchvision path (~14 per frame), but:
- it issues ~83 small operations from Python instead of ~38, and on this CPU each costs ~50–100 µs to issue;
- it was sized for 1000 candidates (a 1000×1000 IoU matrix, 112 kernels, 3 ms GPU time), while the test video never had more than **3** candidates above the threshold in a frame (reported by the run itself).

So it made M15 slower (40.3 → 34.6 FPS). It would only win captured inside the CUDA graph and sized to the data, and even then by at most ~1 ms per frame on this video.

**5. Measurement conditions matter.** The first M15 round (23.10) gave ~10 FPS for every stage and showed no gain from any step. The same kernels ran up to ~2× slower than later and drifted within each run, most likely because the clocks were not pinned and the chip was throttling (power mode not recorded). The rules that came out of this are in [measurement-protocol.md](measurement-protocol.md).

## Open points
- FP16 accuracy has not been measured (needs the labelled test set and an evaluation script).
- Capturing preprocessing and NMS in the CUDA graph (with a small k).
- Engine-level work on the layout conversion kernels (Nsight Compute).
