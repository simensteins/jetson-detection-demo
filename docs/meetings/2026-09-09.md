    On the Time row in Nsight Compute's raw data: it's a real, accurate timestamp of when during the profiling session ncu finished capturing that particular kernel — but it's not useful for judging how fast your model actually runs, because ncu uses kernel replay: to collect detailed hardware counters, it pauses your whole application and re-executes each kernel multiple times (the GPU can only expose a limited set of performance counters per real execution, so gathering a fuller metric set means running the same kernel several times over, each pass measuring something different, then merging the results into that one row). That pause-and-replay cycle is slow — a kernel that natively takes 300 microseconds can take 2-3 seconds of wall-clock time for ncu to fully instrument.

    So the multi-second gaps you saw between consecutive Time entries reflect ncu's own profiling overhead, not real inference timing. The kernel order in that column is still correct (kernel 0 really did run before kernel 1), just the spacing between them is artificially inflated. For actual kernel speed, use the Duration \[us\] column instead — that's the genuine, accurate execution time of each kernel, unaffected by the replay overhead.

## Profiling findings (session summary)

**Tooling setup**

- nsys and ncu now working end-to-end on the Jetson (JetPack 7.2.1). Had to update nsys via apt to a newer release (JetPack-bundled 2022.4.2 hung during report export - GpuTicksConverter/"No GPU associated to the given UUID"). Had to clear `DEBUGINFOD_URLS` each session (symbol download hangs) and re-export `LD_LIBRARY_PATH` each session (injection library) - both are session-local env vars, easy to forget after opening a new terminal.
- ncu needs `sudo` (GPU perf counters are admin-restricted). Use `sudo -E $(which ncu) ...` - bare `sudo ncu` fails since sudo doesn't inherit PATH.
- Viewing reports on the Mac needs a matching-ish Nsight version - big version gaps (e.g. Jetson's old 2022.4.2 vs Mac's 2026.4.1) block `.qdstrm` import entirely. A finished `.nsys-rep` (not `.qdstrm`) opens fine regardless of version since the GUI is backward-compatible with that format.

**NVTX pipeline breakdown (imgsz=640, RTSP + hardware decode, FP32/TF32 baseline)**

- inference: 72.8% (28.3ms) \| decode: 19.3% (7.5ms) \| draw: 7.9% (3.1ms)
- Inference dominates - correctly the focus of optimization effort.

**Resolution scaling (imgsz vs steady-state FPS)**

- 640 → \~23fps, 960 → \~17.9fps, 1280 → \~12.6fps (RTSP + hardware decode)
- Fits fixed-cost + linear-in-pixel-count model reasonably well. 1280 is well under half the 30fps live-feed target; RTSP pipeline drops frames it can't keep up with, so real-world coverage at 1280 would be much worse than the fps number alone suggests.

**Methodology lesson: verify which model is actually loaded**

- A `git checkout -- configs/default.yaml` (done to resolve a pull conflict) silently reverted `model:` from the TensorRT `.engine` back to the committed `yolov8n.pt`. Several "FP16 test" results were actually raw PyTorch/cuDNN execution, not TensorRT at all - caught via `ncu` kernel names (cuDNN kernels like `implicit_convolve_sgemm`, `ampere_sgemm_*`, Winograd kernels have no `_trt` suffix, unlike genuine TensorRT-compiled kernels). Always spot-check `ncu` kernel names for `_trt` suffix before trusting a "TensorRT" result.

**FP16 investigation**

- Confirmed genuine FP16 execution via `ncu` kernel names once the model-loading bug was fixed: `f16f16_f16f16_f16` + `hmma`/`tensor1688`/`tensor16x8x16` (real Tensor Core MMA), vs `f32f32`/`tf32f32` in the FP32 baseline.
- NVTX-measured inference time with FP16: \~33.4ms - actually *slower* than FP32's 28.3ms, consistently across two separate export configs (`end2end=True` and `end2end=False`, both \~33.4ms).
- `end2end=False` (tested to remove a suspected FP32 output-side cast) made no measurable difference - rules out I/O boundary casting as the main cost.
- Working theory: YOLOv8n (smallest variant) has kernels small enough to already be latency/overhead-bound rather than compute-bound, so Tensor Core FP16 throughput advantage doesn't materialize - and may add cost via extra cast/layout kernels at precision boundaries (new kernel types appeared in the FP16 graph with no FP32 counterpart: `permutationKernelPLC3`, `generatedNativePointwise`, `copyPackedKernel`, plus a dedicated `image_first_layer_f16f16_f32_f16` input-cast kernel).

**Major finding: where "inference" time actually goes (nsys `--trace=cuda,nvtx`, one steady-state frame)**

- One full inference pass = 223 CUDA kernel launches.
- Of the 28.5ms NVTX `inference` window:
  - Kernel execution (actual GPU compute): 10.75ms (37.7%)
  - CUDA Runtime API overhead (CPU-side dispatch): 8.31ms (29.2%)
  - Synchronization: 0.75ms (2.6%)
  - Memcpy + Memset: 0.11ms (0.4%)
  - Unaccounted (pure Python/Ultralytics overhead, no CUDA activity): \~8.58ms (30.1%)
- Runtime API breakdown: the three kernel-launch call variants (`cudaLaunchKernel_v7000` 93x, `cuLaunchKernel` 65x, `cuLaunchKernelEx` 65x = 223, one per kernel) total **6.51ms - 78% of Runtime overhead, 23% of total inference time.** This is pure per-kernel dispatch cost.
- Notably, `cudaStreamIsCapturing` was called 64 times - the CUDA/TensorRT stack is already probing for CUDA Graph capture opportunities, but not actually using one.

**Optimization priority (revised given the above - precision was never the main lever)**

1. **CUDA Graphs** - capture the 223-kernel sequence once, replay as a single launch. Directly targets the 6.51ms/23% dispatch-overhead finding. Likely requires dropping to TensorRT's raw Python API rather than Ultralytics' `model.predict()` wrapper.
2. **Better kernel fusion at export** - 223 kernels for a nano model is a lot; check TensorRT builder optimization level / ONNX graph simplification before the TensorRT build step.
3. **Investigate the \~30% pure-Python overhead** - not a CUDA problem, needs `osrt` trace or `cProfile` on one `predict()` call.
4. **FP16** - keep if harmless, but it's capped at \~19% best-case improvement (only touches the 37.7% kernel-execution slice) and measured data shows it isn't winning for this model - not the primary lever.
