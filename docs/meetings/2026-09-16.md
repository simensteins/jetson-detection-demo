# Møte 16.09
*Exported from Notion (page last edited 2026-10-01).*

Summary of all optimization iterations on the YOLOv8n TensorRT detection pipeline (Jetson Orin Nano, JetPack 7.2.1) so far - what changed, why, and the measured result for each. Full detail/methodology for each iteration is on its own page; this page is the condensed overview for the meeting, plus a single comparison table at the bottom.

---

## Baseline

**Setup**: `yolov8n.pt` (COCO) exported to a TensorRT `.engine`, FP32/TF32, run through unmodified Ultralytics `model.predict()` per frame - CPU-side preprocessing (cv2 letterbox/resize + numpy reformat) and CPU-triggered NMS, no CUDA Graph.

**Why this config**: starting reference point - nothing optimized yet, so every later change can be measured against it.

**Result**: 24.90ms mean inference time (29.89 FPS true end-to-end). \~223 individually-dispatched CUDA API calls per frame, \~30% of that time spent as GPU idle gaps between kernels waiting on CPU dispatch. Preprocessing and NMS costs are bundled inside `model.predict()`'s one opaque call - not separable at this stage.

> 📸 **Screenshot placeholder - baseline nsys timeline.** Expect to see: many short, individually-dispatched kernels with visible empty gaps between them; GPU utilization far below 100% through most of the `inference` span; \~223 separate kernel launch events.

---

## Iteration 1 - CUDA Graph

**Changed from baseline**: nothing about preprocessing or NMS - only *how the model itself gets invoked*. The engine's forward pass (previously \~223 individually-dispatched kernels per frame) is captured once into a CUDA Graph and replayed with a single `graph.replay()` call per frame.

**Why**: the baseline's \~30% GPU idle time and \~223 CPU dispatch calls per frame pointed directly at CPU dispatch overhead as the cause - CUDA Graphs are NVIDIA's standard fix for exactly this pattern (bypass per-kernel CPU dispatch by replaying a pre-recorded sequence).

**Result**: inference time 24.90ms -> 19.35ms (**-22.3%**). Idle gap between the model's own kernels collapsed from \~30% to **0.2%** (166 kernels now run back-to-back). This confirmed the theory cleanly - but also revealed two costs the baseline's coarse measurement had been hiding: preprocessing (42.7% of the frame, larger than the model itself) and a gap before NMS's kernels start (12.9%). Neither was touched by this iteration.

> 📸 **Screenshot placeholder - Iteration 1 nsys timeline.** Expect to see: the captured graph replaying as one dense, back-to-back block of kernels with essentially no visible gaps (vs. baseline's spread-out, gapped timeline); a single `cudaGraphLaunch` API call replacing hundreds of individual dispatch calls. Note: `--cuda-graph-trace=node` must be used or the graph shows as one opaque block instead of its individual kernels.

---

## Iteration 2 - GPU Preprocessing

**Changed from Iteration 1**: preprocessing moved from CPU to GPU, in two steps (CUDA Graph from Iteration 1 kept unchanged throughout):

- **2a**: reformatting (BGR->RGB flip, normalize, HWC->CHW transpose) moved to GPU tensor ops; resize/letterbox still on CPU (`cv2`).
- **2b**: resize/letterbox moved to GPU too (`torch.nn.functional.interpolate` + `F.pad`), so preprocessing is now fully GPU-side.

**Why**: Iteration 1 showed preprocessing was now the single largest cost in the frame (42.7%, 8.27ms) - larger than the model itself. The Jetson's GPU has \~170x more parallel execution units than its CPU (1024 CUDA cores vs 6 CPU cores), and preprocessing is an embarrassingly parallel, per-pixel workload - exactly what that gap rewards.

**Result**: preprocessing 8268us -> 1641us (**-80.2%**), pulling total inference down to **12.84ms (-48.4% vs. baseline)**. Model execution and its idle-gap win stayed correctly unchanged (confirms this step was isolated to preprocessing). Realized speedup (\~5x) was smaller than the raw \~170x core-count ratio, as expected - `cv2`'s CPU resize already uses SIMD, and GPU kernel-launch overhead doesn't shrink with more cores. New bottleneck exposed: the pre-NMS gap grew to the second-largest cost (2.46ms, 19.2% of the frame) now that preprocessing shrank.

> 📸 **Screenshot placeholder - Iteration 2 nsys timeline.** Expect to see: the block of activity before the model's first `_trt` kernel shrinking dramatically - from a long CPU-side gap (cv2 running on CPU, invisible to the GPU timeline) down to a short run of small GPU kernels (flip/resize/pad) right before the model starts.

---

## Iteration 3 - Custom Fixed-Shape NMS

**Changed from Iteration 2**: replaced Ultralytics' `non_max_suppression()` (dynamic-shape boolean-mask filtering, forces GPU->CPU syncs) with a custom fixed-shape "Fast NMS": `torch.topk(k=100)` for a deterministic-size candidate set + a fully vectorized IoU-matrix suppression pass. Also fixed a bug found during analysis where `draw_detections()` was doing three separate GPU->CPU syncs instead of one, quietly reintroducing dispatch overhead downstream of NMS.

**Why**: Iteration 2 exposed a 2.46ms gap between the model's last kernel and NMS's first kernel (19.2% of the frame) - Ultralytics' NMS needs to know how many detections passed the confidence threshold before it can size its next operation, which forces a sync each time. TensorRT's own EfficientNMS plugin (`end2end=True`) was tested and confirmed *not* to work on this TensorRT version (10.16.2.10 - the plugin variant was removed in 10.16), ruling out that alternative; a fixed-shape rewrite (NVIDIA's own recommended CUDA Graph pattern: pad to max size + mask, never resize) was the remaining option.

**Result**: the NMS setup gap + NMS execution collapsed from 3111.49us to **503.96us** (**-83.8%**). True end-to-end throughput (the metric that matters, since the sync-relocation fix moved cost between NVTX buckets without changing wall-clock time): **55.10 FPS -> 74.22 FPS (+34.7% vs. Iteration 2, +148.4% vs. baseline)**.

> 📸 **Screenshot placeholder - Iteration 3 nsys timeline.** Expect to see: the long gap between the model's last kernel and NMS's first kernel almost disappearing - NMS's kernels (`gatherTopK`, `triu_tril_kernel`, etc.) now start almost immediately after the model's last kernel, instead of after a long CPU-dispatch-bound stretch.

## Results comparison

All rows measured the same way: `jetson_clocks` locked, local file source (`data/vtest.avi`), `nsys profile --trace=cuda,nvtx --cuda-graph-trace=node`, 50-frame warm-up skipped. "True end-to-end" = wall-clock time from `decode` start to `draw` end, computed directly from raw NVTX timestamps (the most trustworthy number - NVTX-bucket totals alone can be misleading when a fix moves cost between buckets, as happened in Iteration 3).

| Version | What changed | Total inference (NVTX) | True end-to-end frame time | FPS | vs. Baseline |
| --- | --- | --- | --- | --- | --- |
| Baseline | - | 24.90ms | 33.45ms | 29.89 | - |
| Iteration 1 | • CUDA Graph | 19.35ms | 24.73ms | 40.43 | +35.3% |
| Iteration 2 | • GPU preprocessing (2a+2b) | 12.84ms | 18.15ms | 55.10 | +84.3% |
| **Iteration 3** | **• Custom fixed-shape NMS** | **10.13ms** | **13.47ms** | **74.22** | **+148.4%** |

The pipeline now runs at roughly **2.5x** the original baseline throughput, via three independent, individually-verified changes - each one targeting the specific bottleneck the previous change exposed.
