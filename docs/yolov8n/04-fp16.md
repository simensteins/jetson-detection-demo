# Iteration 4 – FP16 through the whole pipeline (YOLOv8n)

Script: `scripts/infer_cuda_graph_fp16.py` · engine: `yolov8n_fp16_io.engine` (built with `scripts/export_yolo_fp16.py`) · builds on [Iteration 3](03-custom-nms.md).

## What changed
- **FP16 engine with FP16 input and output.** An earlier attempt made only the engine FP16 and left preprocessing and NMS in FP32; TensorRT then adds conversion kernels at both ends every frame. Here the input buffer is FP16, preprocessing computes in FP16, and the output stays FP16 until NMS.
- **One deliberate FP16 → FP32 conversion**, after the top-k in the custom NMS: box areas reach 640 × 640 = 409,600, beyond FP16's maximum of 65,504.
- **The script checks the engine.** It prints both I/O dtypes and refuses to run unless both are `torch.float16` (`confirmed: engine I/O is FP16 end-to-end`).

## Building the engine
Ultralytics' `YOLO(...).export(format="engine", half=True)` builds FP16 layers but keeps **FP32** input/output (checked with `scripts/inspect_engine.py`: `images`/`output0` dtype `FLOAT`). So:

```bash
cp yolov8n.pt yolov8n_fp16.pt     # keeps Ultralytics from overwriting yolov8n.engine
python3 -c "from ultralytics import YOLO; YOLO('yolov8n_fp16.pt').export(format='engine', half=True, imgsz=640)"
python3 scripts/export_yolo_fp16.py --mem-pool-mb 2048    # -> yolov8n_fp16_io.engine
python3 scripts/inspect_engine.py yolov8n_fp16_io.engine  # images / output0: HALF
```

`export_yolo_fp16.py` takes the ONNX file Ultralytics leaves behind, builds it with `trtexec --fp16 --inputIOFormats=fp16:chw --outputIOFormats=fp16:chw`, checks that both I/O tensors are HALF, and writes it behind Ultralytics' metadata header so `YOLO(...)` loads it as before.

Two FP16 engines found on the Jetson (`yolov8n_fp16.engine`, `yolov8n_fp16_e2e.engine`, 85 MiB each) had been built with a newer TensorRT (serialization version 243 vs. the venv's 240) and could not be loaded at all; they are kept in `old_engines/` on the Jetson.

## GPU preprocessing fix (applies to Iterations 2–4)
Iterations 2–4 were written on `vtest.avi` (768×576). On the 1920×1080 test video their GPU preprocessing took ~2.5 ms of GPU time per frame (FP16: 1.7 ms): the full frame was flipped BGR → RGB, converted to float and divided by 255 before being resized. Since commit `80e8e30` they convert once, resize, then flip and normalize the 640×360 result directly into the letterbox. FP32 output is identical to the old code; FP16 within one rounding step. FP16 preprocessing: 1.71 → 0.95 ms GPU.

## Result (paper set, 25 W)

| | + Custom NMS (Iteration 3) | + FP16 (Iteration 4) |
|---|---|---|
| FPS | 72.7 | **86.7** |
| Frame time | 13.75 ms | 11.53 ms |
| GPU kernel execution | 9.16 ms | 5.01 ms |
| GPU idle | 0.07 ms | 1.90 ms |

The model's GPU time halves. GPU idle time grows again because **the pipeline is now CPU-bound**: the GPU finishes its work and waits for Python to issue the next operations (preprocessing and NMS are still launched one PyTorch call at a time). The next step would be capturing preprocessing and NMS in the same CUDA graph as the model.

Accuracy of the FP16 engine has not been measured yet; see [FP16 research](../research/fp16-research.md) for the evaluation method (`model.val()` on COCO).
